## 阻塞发现

### R2-1 / P1：幂等预留先提交，存储失败后同 key 无法恢复（B4 未关闭）

位置：`agent_net/persistence/code_review_store.py:1191`；`agent_net/node/routers/code_review.py:610`–`:620`。

reserve_artifact_idempotency 单独提交映射，随后才写 Vault 和 artifact。注入一次 Vault OSError，首次返回 **503 temporarily_unavailable**；恢复存储后完全相同请求/key 重试返回 **409 delivery_conflict**，因为预留 artifact_id 尚无 artifact，replayed 分支直接拒绝。映射永久占用，没有恢复状态。同 key 并发请求也可能观察到此窗口。内容寻址解决了原字节覆盖，但没有完成失败后可恢复幂等。

要求：持久化 pending/committed 状态及安全恢复机制，或使幂等映射与 artifact 登记原子提交；并发重放不能被当成不同内容冲突。补 Vault 失败、artifact INSERT 失败、提交前崩溃及并发同 key 的重试测试。

### R2-2 / P1：上传仍未绑定真实 Run/Attempt/epoch，未知资源授权会放行（B2 未关闭）

位置：`agent_net/node/routers/code_review.py:591`–`:598`；`agent_net/code_review/service_auth.py:136` 起的 require_resource。

get_profile_session 找不到 Run 时得到空 session；require_resource 在目标 session 为空、凭据登记了任意资源范围时不拒绝。实测只授权一个 session 的 worker 给 **unregistered-run / unassigned-attempt / epoch=999** 上传，返回 **201**。对真实 Run 传不存在的 Attempt 和 epoch=999 也返回 **201**：代码只查 worker 角色，没有查分配、租约或 epoch。RC2 §4 的“被分配 worker”并未落实，上传绑定字段成为可任意填写的标签。

要求：未知或歧义 Run 先拒绝；从受信任 Coordinator/Run 关联解析唯一 session，检查认证 worker、Attempt、当前 epoch 及取消/过期状态，并与登记操作保持一致性。不能只把空 session 的分支补上而继续忽略 Attempt。

相关资源边界还需覆盖：GET message 的当事人分支（`:476`）绕过 require_session；若同 DID 在多个 session 使用，凭据的 session 限制仍应执行。

### R2-3 / P1：回执仍先独立落库，被拒绝的冲突消息产生业务记录（B6 未关闭）

位置：`agent_net/node/routers/code_review.py:401`、`:425`；`agent_net/persistence/code_review_store.py:431`、`:1245`。

路由先调用 create_profile_receipt（独立连接提交），再 store_message_with_receipt。后者只原子写 inbox 及其 receipts_json，并未把真实 code_review_receipts 插入纳入同一事务。实测先提交合法 receipt，再以相同 message_id、更换 receipt_id 提交：HTTP **409 idempotency_conflict**，但新 receipt 已出现在数据库。进程在两步间退出也会留下无对应 inbox 的权威记录。

另需一并处理 receipt_id 重用：create_profile_receipt 对已存在 ID 直接返回旧记录，不比较 payload/资源，不能把不同 Run 或不同决定静默重放成旧 receipt。

要求：先在事务中验证消息/回执幂等投影，再原子写业务回执、inbox 和 processed；冲突无副作用。补冲突后全表不变和每个事务故障窗口测试。当前 GET 补偿机制解决了旧窗口的部分症状，不代表完整原子性已实现。

### R2-4 / P1：合法 validator/publisher 被额外要求 coordinator（B1 修复引入的角色回归）

位置：`agent_net/node/routers/code_review.py:385`–`:395`。

receipt 经 require_receipt_authority 后把 required_role 置 None，随后 `_enforcement_level(principal, required_role or "coordinator")` 一律查 coordinator。实测独立 validator 凭据、正确 session/DID，并登记 validator role grant，提交合法 validated 回执返回 **403：不具备所需角色 coordinator**。publisher 同理。仅在没有 role_grants 时绕过，因此现有测试不能证明启用严格角色表后的分工能工作。

要求：从 receipt kind 取得唯一 required_role，身份与强制级别均复用该映射及资源范围；不能给 validator/publisher 补 coordinator 来绕过。增加四种回执 kind 在真实 role_grants 下的正反例，以及 worker 混合高权限角色的配置拒绝测试。

### R2-5 / P1：null findings 仍被转换为空列表，误报无发现（B7 未完全关闭）

位置：`agent_net/code_review/provider_adapter.py:172`–`:174`。

新 `_strict_list` 拒绝了字符串元素，但 `raw is None` 仍直接返回 []，把显式 null 与不存在字段混同。实测合法原生 schema、outcome=findings_present、**findings=null**、coverage=complete，经公共管线仍得到 **no_findings / []**。此前 malformed-finding 负例已修复，但同类错误输入仍会改变结论；缺口数组 null 也受同一分支影响。

要求：按原生契约区分必填字段缺失和可选字段缺省，显式 null/类型错误不得静默为空；不支持原生结构时 invalid_output。补 null、缺失、错误集合类型与 coverage 缺口集合的反例。

### R2-6 / P1：拒绝证据仍未按冻结 schema 与具体用例语义验证（B9 未关闭）

位置：`specs/profiles/code-review/v1/tools/check_evidence.py:426`–`:460`。

当前只检查错误必填键是否存在及 code 枚举，没有调用冻结错误 schema；subject/endpoint 只要求非空，没有与拒绝用例绑定。实测 response_status=403、subject=unrelated-admin、endpoint=`GET /unrelated/health`，响应正文设置 **schema=not-an-error-schema、retryable="yes"、action_required=null、scope=123、retry_after_seconds=-99**，verify_refusal_sample 仍返回 **True、failures=[]**。用例标签不能证明 worker 发布或伪造 receipt 被拒绝，修复确认所称“原始字节能解码为冻结错误信封”仍不成立。

要求：真正运行 error.schema.json（包含类型、const、additionalProperties 和不变式），按每种拒绝场景验证主体角色/凭据条件、方法及端点、预期错误码与响应状态；缺失关联证据则不闭合该项。测试必须包括合法 403 但错误场景，以及具有全部键但 schema 不合法的响应。本复现针对拒绝检查，不声称一条样例即可绕过全部 25 项门禁。
